Added a "Manage Credentials" modal for Ceph/S3 Object Storage, so a user can finally see, create, and delete their own EC2 (S3) access keys. Until now the secret never reached them at all: `create` returned `{ access, secret }`, the empty state discarded the response, invalidated the bucket list and reloaded the page, and the key went on working only inside Aurora — the BFF reads it out of Keystone itself to sign every Ceph request.

The modal is reachable from three places: the overflow ("More Actions") menu next to "Create Bucket" on the bucket list, the rewritten "S3 Object Storage: Setup Required" empty state (which no longer creates a credential itself or reloads the page — it just opens the same modal, and is now built on Juno's `Status`, the same component the bucket list's other full-page states use), and the previously dead-end "S3 Credentials No Longer Valid" screen, which now offers a "Manage Credentials" action instead of prose with nowhere to go.

Inside the modal:

- **Access Keys** lists every EC2 credential the user holds in the project in a three-column table: the access key ID in full (it's the only way to tell two keys apart — Keystone's EC2 credential object carries no name/label), the secret beside it, and a delete button. Both values sit in read-only monospace text fields wide enough for the whole value, which is also how they are copied — a value selects out of a field perfectly well, so neither carries a copy control of its own.
- **Secrets are concealed by default and fetched only on demand.** Each secret field is an `InputGroup` of a read-only `type="password"` input and its own "Reveal"/"Hide" button. Until "Reveal" is clicked the field holds filler of the same length as a real secret, so opening this modal to read the endpoint fetches no secrets at all; "Reveal" spends one `storage.ceph.ec2Credentials.reveal` call for that one key, and "Hide" discards the value rather than masking it, as do deleting the key and closing the modal. `type="password"` only changes how an input paints a value it already has, so the thing that actually keeps a secret out of reach is not having fetched it. `list` still strips secrets, and `reveal` is a mutation rather than a query on purpose — a query result lands in and survives inside the TanStack Query cache (visible in devtools) until it is garbage-collected — and the modal calls it through the vanilla tRPC client rather than `useMutation`, so the answer is held by nothing but the component's own state. A failed reveal is reported once in the modal's single error message, naming the key it belongs to, rather than as a validation message on that field; the other key is unaffected and clicking "Reveal" again retries.
- **Connection Details** shows the S3 endpoint and region, sourced from an extended `storage.ceph.containers.status`, which now also returns `endpoint`/`region` (previously only `hasCredentials`). This procedure intentionally does not require existing credentials, so Connection Details renders correctly even for a user who has none yet.
- **Creating** a key adds its row concealed like every other one, and its secret is read through that row's own Reveal. `create` no longer returns the secret at all: it generates one, hands it to Keystone and answers with `{ id, access, user_id, project_id }`, so `reveal` is the single procedure that ever puts a secret on the wire. There is then no place in the modal where a secret appears without being asked for, and nothing has to be caught at creation time. A toast alongside it names the new access key and says where to find it again ("More Actions", then "Manage Credentials"): the very first key in a project is created from the empty state by someone who has never seen this modal and reached it through a menu they had no reason to open, so without that pointer the modal is a dead end found by accident.
- **Deleting** a key goes through a confirmation dialog stacked on top of the modal (the same shape `ObjectVersionHistoryModal` already uses for its own delete). The dialog names the key and says what is lost: it stops working immediately, any S3 client configured with it loses access, and a replacement is a new key with a new secret. Deleting the *last* key says one thing more, because that one is not just one fewer key: without a credential the BFF cannot sign a Ceph request at all, so S3 Object Storage goes out of reach in the dashboard too — the dialog says so, and also that nothing stored is lost and a new key reaches the same buckets. Confirming closes the dialog, a spinner replaces that row's button while the request is in flight, and a toast reports the outcome either way: the deleted access key on success, and on failure whatever the identity service answered. `delete` is deliberately not idempotent — a credential that is already gone answers `NOT_FOUND` rather than reporting a deletion that did not happen — and the key list is refreshed on a failure too, so a row for a credential Keystone no longer has does not stay on screen — taking any secret that row had revealed with it, since the Hide that would otherwise discard it goes with the row. The row's own button is labelled after its key, so two rows don't offer two buttons reading the same thing.
- There is **no ceiling** on how many access keys a user may hold in a project. Neither Keystone nor RGW imposes one, and all of a user's keys in a project map to the same RGW identity, so an extra key grants no extra access and costs no quota — a limit in the dashboard would only be Aurora refusing what the backend is willing to do. `create` accordingly posts straight to Keystone instead of reading the existing list first, which also takes a round trip off every creation. The "Create Access Key" button sits above the key table rather than in the modal footer.

Behaviour changes worth noting for consumers:

- `storage.ceph.containers.status` now returns `endpoint` and `region` alongside `hasCredentials`. Purely additive for consumers, who only ever see the shape through `AuroraRouter`.
- New public procedure: `storage.ceph.ec2Credentials.reveal`.
- **Breaking for direct API consumers:** `storage.ceph.ec2Credentials.create` no longer returns `secret`. It answers `{ id, access, user_id, project_id }`; the secret is read through `reveal`. Nothing in the dashboard consumed it.
- New permission key `storage:credentials:delete`. **Operators with a forked `storage.json` should add `"storage:credential_delete": "rule:storage_viewer"` (or their own equivalent rule)** — otherwise the "Delete" action on access keys stays hidden. This PR also hardens `createPermissionRouter` so a single missing/misconfigured rule no longer fails an entire `canUser` batch (it previously threw and took down every other permission requested alongside it); the missing rule now just resolves to `false` for that one key, same as before this PR for any other Ceph permission.
- `resolveEC2Credential` (used internally on every Ceph request to pick which credential to sign with) now sorts by credential `id` instead of taking whatever Keystone returns first, so which of a user's keys the BFF authenticates as is stable across requests instead of depending on Keystone's unspecified response order. EC2 credentials carry no timestamp, so this is a deterministic choice, not a "most recent" one — there is still no concept of an "active" key.
- Files under `Ceph/Buckets/-components/CredentialPrompt.*` moved to a new `Ceph/Credentials/` directory alongside the new modal; nothing under `Ceph/Buckets/` imports this from outside the package.

Swift is unaffected — it does not use EC2 credentials.
